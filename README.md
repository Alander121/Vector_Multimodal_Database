# Video Multimodal Search

Система для индексирования видеозаписей и поиска визуально похожих кадров по загруженному изображению. Приложение извлекает кадры из видео, строит для них визуальные векторные представления с помощью **SigLIP2** и **DINOv2**, сохраняет файлы в S3-совместимое хранилище, метаданные — в **PostgreSQL**, а векторные индексы — в **FAISS**.

Проект рассчитан на локальный запуск или развёртывание на одном сервере с помощью Docker Compose. GPU используется при наличии корректно настроенного и доступного PyTorch-устройства; иначе обработка выполняется на CPU.

## Возможности

- Обнаружение видеофайлов во входном каталоге без предварительного формирования полного списка путей.
- Поддержка видеоформатов MP4, MOV, AVI, MKV и WEBM.
- Извлечение кадров с настраиваемой частотой, по умолчанию — **0,5 кадра в секунду**.
- Генерация двух визуальных embeddings для каждого кадра:
  - **SigLIP2** (`google/siglip2-base-patch16-224`);
  - **DINOv2** (`facebook/dinov2-base`).
- Получение векторов размерности 768 с типом `float32`.
- Нормализация векторов перед использованием в поиске.
- Хранение метаданных видео и кадров в PostgreSQL.
- Хранение JPEG-кадров в S3-совместимом хранилище MinIO.
- Хранение резервных копий векторных данных в PostgreSQL и поисковых индексов в FAISS.
- Поиск визуально похожих кадров по загруженному изображению.
- Предварительная обработка изображений и сохранение JPEG-данных для передачи в объектное хранилище и вычисления SHA-256 без повторного JPEG-кодирования.
- Повторный запуск индексирования с пропуском уже обработанных материалов в соответствии с проверками приложения.
- REST API на FastAPI и интерактивная документация OpenAPI, если она не отключена конфигурацией.

## Архитектура

```text
                       Входные видео
                            |
                            v
                  Обнаружение видеофайлов
                            |
                            v
                    Извлечение кадров
                     (sample FPS)
                            |
               +------------+------------+
               |                         |
               v                         v
          SigLIP2 model              DINOv2 model
               |                         |
               v                         v
         embedding 768              embedding 768
         float32                    float32
               |                         |
               +------------+------------+
                            |
              +-------------+-------------+
              |             |             |
              v             v             v
         PostgreSQL       MinIO         FAISS
         metadata         JPEG          vector indexes
         vector backup    frames        similarity search
              ^                            |
              |                            v
              +--------- FastAPI <--- query image
                            |
                            v
                  Результаты поиска
```

### Назначение компонентов

| Компонент | Назначение |
|---|---|
| **PostgreSQL** | Метаданные видео и кадров, связи между ними, служебная информация и резервные копии embeddings. |
| **MinIO** | Объектное хранение извлечённых JPEG-кадров через S3 API. |
| **FAISS** | Поиск ближайших векторов по визуальным embeddings. Используется HNSW с inner product для нормализованных векторов. |
| **SigLIP2** | Получение визуального embedding кадра для одного пространства признаков. |
| **DINOv2** | Получение дополнительного визуального embedding кадра. |
| **FastAPI** | HTTP API для проверки состояния сервиса и выполнения поиска. |
| **Docker Compose** | Запуск API, PostgreSQL и MinIO в общем окружении. |

Векторные индексы FAISS загружаются приложением при запуске API. Поэтому после перестроения индексов на диске API необходимо перезапустить, чтобы он перечитал обновлённые файлы индексов.

## Требования

1. Linux, Windows с Docker Desktop/WSL2 или другая среда, поддерживающая Docker Engine.
2. Установленные Docker Engine и Docker Compose Plugin.
3. Достаточное дисковое пространство для исходных видео, JPEG-кадров, базы данных, моделей и FAISS-индексов.
4. Доступ к Hugging Face при первом запуске для загрузки моделей, если они ещё не находятся в локальном кэше.
5. Оперативная память, достаточная для выбранного размера набора данных и FAISS-индексов.

GPU не является обязательным условием. При отсутствии совместимого CUDA-устройства вычисления выполняются на CPU. Время индексирования на CPU может быть существенно больше.

## Запуск

### 1. Получение проекта

Перейдите в корневой каталог проекта — туда, где находится `compose.yaml` или `docker-compose.yml`.

```bash
cd /path/to/video_multimodal_search_pg_faiss_v2_2
```

### 2. Проверка конфигурации

Проверьте значения переменных окружения в `.env` и/или `compose.yaml`. Основные параметры приведены в разделе [Конфигурация](#конфигурация).

Для соединения сервисов внутри Docker Compose используются имена сервисов, а не `localhost`. В частности, строка подключения PostgreSQL для контейнеров имеет вид:

```text
postgresql://video:video@postgres:5432/videodb
```

Параметры MinIO для локальной конфигурации:

```text
Endpoint:  minio:9000
Access:    minioadmin
Secret:    minioadmin
Bucket:    video-frames
```

Указанные учётные данные предназначены только для локального тестового окружения. Для общего сервера замените их на собственные секреты и не публикуйте `.env` в Git.

### 3. Сборка и запуск контейнеров

```bash
docker compose up -d --build
```

Проверить состояние контейнеров:

```bash
docker compose ps
```

Посмотреть логи API:

```bash
docker compose logs -f api
```

Посмотреть логи всех сервисов:

```bash
docker compose logs -f
```

При первом запуске приложение может загружать модели SigLIP2 и DINOv2 из Hugging Face. Это занимает время и требует сетевого доступа. После загрузки модели должны использовать локальный кэш, если каталог `HF_HOME` сохраняется между перезапусками контейнера.

### 4. Проверка доступности API

```bash
curl http://localhost:8000/health
```

FastAPI обычно предоставляет интерактивную документацию по адресу:

```text
http://localhost:8000/docs
```

Порты локального окружения:

| Сервис | Адрес на хосте | Назначение |
|---|---|---|
| API | `http://localhost:8000` | HTTP API и документация |
| PostgreSQL | `localhost:5432` | База метаданных |
| MinIO API | `http://localhost:9000` | S3 API |
| MinIO Console | `http://localhost:9001` | Веб-интерфейс MinIO |

## Добавление и индексирование видео

Видеофайлы должны быть доступны внутри контейнера API по пути `/app/data/videos`. В `compose.yaml` проверьте соответствие этого пути каталогу на хостовой машине. Например, если настроено монтирование `./data/videos:/app/data/videos`, файлы нужно положить в `data/videos` в корне проекта.

Поддерживаемые расширения:

```text
.mp4 .mov .avi .mkv .webm
```

Запуск индексирования:

```bash
docker compose exec api python -m app.ingest --dir /app/data/videos
```

При необходимости частоту извлечения кадров можно указать явно:

```bash
docker compose exec api python -m app.ingest \
  --dir /app/data/videos \
  --sample-fps 0.5
```

`--sample-fps 0.5` означает извлечение в среднем одного кадра каждые две секунды. Увеличение частоты повышает число кадров, объём хранения и время генерации embeddings. Уменьшение частоты сокращает эти затраты, но может привести к пропуску коротких событий.

Во время индексирования в логах отображаются обнаружение видео, характеристики ролика, обработка кадров и итоговое количество добавленных или пропущенных материалов. Повторная обработка ранее проиндексированных файлов зависит от проверок идентичности и состояния, реализованных в ingest-процессе.

## Поиск по изображению

Поиск выполняется отправкой изображения в endpoint `/search/image`.

Пример запроса из каталога, где находится `RandomUAV.png`:

```bash
curl -X POST "http://localhost:8000/search/image?limit=20" \
  -F "file=@RandomUAV.png"
```

Параметр `limit` задаёт максимальное количество результатов, запрашиваемых API.

Поисковый процесс использует визуальные представления SigLIP2 и DINOv2 и соответствующие индексы FAISS. Параметры объединения результатов и количество кандидатов регулируются конфигурацией приложения.

Пример проверки через Python или сторонний HTTP-клиент также можно выполнить по адресу API `http://localhost:8000`; точная схема ответа доступна в OpenAPI-документации `/docs`.

## Перестроение FAISS-индексов

Если индексы отсутствуют, повреждены или их количество векторов не соответствует данным PostgreSQL, выполните перестроение:

```bash
docker compose exec api python -m scripts.rebuild_faiss
```

После успешного завершения перезапустите API:

```bash
docker compose restart api
```

Это необходимо, поскольку работающий API держит загруженные FAISS-индексы в памяти. Перестроение файлов на диске само по себе не обновляет уже загруженные в память структуры.

Перестроение может потребовать значительного объёма оперативной памяти и дискового пространства: для каждого кадра сохраняются два исходных вектора размерностью 768 `float32`. При увеличении набора данных следует отдельно контролировать пиковое потребление RAM и размер индексов.

## Конфигурация

Основные параметры моделей, обработки и поиска:

| Переменная | Значение по умолчанию | Назначение |
|---|---:|---|
| `SIGLIP_MODEL` | `google/siglip2-base-patch16-224` | Модель SigLIP2 |
| `DINO_MODEL` | `facebook/dinov2-base` | Модель DINOv2 |
| `DEVICE` | `auto` | Выбор устройства вычислений |
| `EMBED_BATCH_SIZE` | `4` | Размер пакета при генерации embeddings |
| `FRAME_SAMPLE_FPS` | `0.5` | Частота извлечения кадров |
| `HF_HOME` | `/models/huggingface` | Каталог кэша моделей Hugging Face |
| `FAISS_DIR` | `/app/faiss_index` | Каталог файлов индексов FAISS |
| `FAISS_INDEX_TYPE` | `hnsw` | Тип FAISS-индекса |
| `FAISS_HNSW_M` | `32` | Параметр связности графа HNSW |
| `FAISS_HNSW_EF_CONSTRUCTION` | `200` | Параметр построения графа HNSW |
| `FAISS_HNSW_EF_SEARCH` | `64` | Параметр поиска HNSW |
| `SEARCH_FETCH` | `100` | Количество кандидатов для этапа поиска |
| `RRF_K` | `60` | Параметр рангового объединения результатов |
| `SIGLIP_WEIGHT` | `0.60` | Вес результатов SigLIP2 |
| `DINO_WEIGHT` | `0.40` | Вес результатов DINOv2 |
| `TORCH_NUM_THREADS` | `4` | Количество потоков PyTorch на CPU |

Подключение PostgreSQL в контейнерной сети:

```text
postgresql://video:video@postgres:5432/videodb
```

Параметры MinIO:

```text
Endpoint: minio:9000
Bucket:   video-frames
```

Фактические имена переменных для подключения к PostgreSQL и MinIO следует сверять с используемым `.env` и `compose.yaml`: в разных конфигурациях проекта они могут задаваться непосредственно в Compose-файле.

### Настройка поиска и производительности

- `EMBED_BATCH_SIZE` влияет на скорость генерации embeddings и объём временной памяти. При нехватке памяти уменьшите размер пакета.
- `FRAME_SAMPLE_FPS` определяет плотность выборки кадров из видео.
- `FAISS_HNSW_M` влияет на размер графа и качество/стоимость поиска.
- `FAISS_HNSW_EF_CONSTRUCTION` влияет на качество построения HNSW и время индексации.
- `FAISS_HNSW_EF_SEARCH` влияет на компромисс между качеством и задержкой поиска.
- `SIGLIP_WEIGHT`, `DINO_WEIGHT` и `RRF_K` управляют настройками объединения результатов двух визуальных поисковых ветвей в соответствии с реализацией приложения.

Изменение параметров индекса HNSW обычно требует перестроения индексов. После перестроения перезапустите API.

## Проверка работы и диагностика

### Контейнер API перезапускается

Проверьте логи:

```bash
docker compose logs --tail=100 api
```

Если в логах указано, что `torchvision` отсутствует, проверьте, что зависимость `torchvision` установлена в том же Python-окружении и совместима с установленной версией PyTorch. После изменения зависимостей пересоберите контейнер:

```bash
docker compose up -d --build api
```

### Модели не загружаются

Проверьте наличие сетевого доступа к Hugging Face, свободное место в каталоге кэша и логи API. Предупреждение о неавторизованном обращении к Hugging Face само по себе не означает ошибку загрузки модели; важен результат загрузки весов.

### Поиск возвращает пустой список

1. Проверьте, что индексирование завершилось успешно и в логах есть ненулевое количество обработанных кадров.
2. Проверьте доступность PostgreSQL и наличие метаданных кадров.
3. Проверьте наличие файлов FAISS-индексов в `FAISS_DIR`.
4. При необходимости перестройте индексы и перезапустите API.
5. Убедитесь, что API использует тот же каталог FAISS и ту же базу данных, с которыми выполнялось индексирование.

### Изменения индексов не отражаются в поиске

Перезапустите API после перестроения:

```bash
docker compose restart api
```

### Просмотр состояния сервисов

```bash
docker compose ps
docker compose logs --tail=100 postgres
docker compose logs --tail=100 minio
docker compose logs --tail=100 api
```

## Ограничения

- Текущая реализация предназначена для визуального поиска по кадрам. Аудиоэмбеддинги, распознавание речи, OCR и специализированное распознавание объектов БПЛА не входят в описанный рабочий контур.
- Отдельный полноценный semantic search и гибридный поиск по тексту и визуальным признакам не входят в текущий функциональный объём.
- FAISS — библиотека векторного поиска, а не самостоятельная распределённая СУБД. Согласованность FAISS-индексов с PostgreSQL и их обновление контролирует приложение.
- Индексы FAISS загружаются в память API. Потребление RAM зависит от числа векторов, размерности и типа индекса.
- Архитектура не предполагает автоматически подтверждённую производительность на десятках миллионов кадров. Для таких объёмов необходимы отдельные нагрузочные испытания, оценка RAM/SSD, времени ingest, задержки поиска и качества recall.
- Учётные данные, приведённые для локального окружения, необходимо заменить перед размещением сервиса в общей сети или в облаке.
